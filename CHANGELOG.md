## 0.20.0 - 2026-10-29

Commit `711c44e4e7d6`; release record `pub:sha2-256:ntzmjmfymo7jqknb35qnakshrg75n3kimsuumkcon4t4xy7b2zba`.

### Changed
- The main.yml pubkit sync writes skips the tests the merge queue already passed: a first job, tested (job-tested.yml), looks for a successful merge_group run of pr.yml on the pushed commit, which merging moves main to. Found, every job that only tests is skipped and sonar reads the queue run's coverage (job-sonar.yml's new coverage-run input), so main runs only the scan and the release; not found, as in a repository without the queue, every job runs as before. passed counts a job skipped for the queue's run, and the release runs whenever passed succeeds
- The release job pubkit sync writes passes pubrel's release workflow the release app's RELEASE_APP_ID and RELEASE_APP_KEY secrets, by name, when the ci block's pubrel is 0.6.1 or later (the first to take them, and to tag with the app's token), and always to a repository's own release workflow ("release": {"uses": "local"})

### Fixed
- A Sustenaut repository's release-tag ruleset lets through the Sustenaut release GitHub App (app 5529889) instead of GitHub Actions, which GitHub refuses as a bypass actor in an organization's repository ("Actor GitHub Actions integration must be part of the ruleset source or owner organization"), so pubkit protect can put the tag ruleset on the organization's repositories again; other owners' keep GitHub Actions. pubkit protect --check and the board compare against the same
- pubkit protect no longer fails on a private repository with "Invalid rule 'merge_queue'" (HTTP 422): GitHub offers a merge queue only to an organization's public repositories and Enterprise Cloud's private ones, so protect reads each repository's owner and visibility, and a private one's organization plan, and gives main's ruleset without the queue (strict up-to-date checks instead) where there is none, saying so; should GitHub still refuse the merge_queue rule, it warns and tries once more without it

### Internal
- pubkit's own CI skips, on a push to main, the jobs the merge queue already passed on the commit (functional, audit, osv, terraform, deploy-static, cache-action), and runs the scan on the queue run's coverage, then the release and the wheel

## 0.19.0 - 2026-10-29

Commit `a216bfc1d627`; release record `pub:sha2-256:5tzkhxqqm5h55jhraiesgeuitesv27sjtwpiq2ixli3tx7wfynsa`.

### Changed
- pubkit's main ruleset merges through GitHub's merge queue (merge commits, one group of up to five at a time) instead of requiring a branch to be up to date with main: the queue runs the required checks on the pull request merged into main as main will hold it, so the tree the checks passed is still the tree main holds after the merge and tagging a release needs no tests of its own, and pull requests stacked behind one another merge one at a time without anyone updating a branch. GitHub offers a merge queue only to an organization's public repositories, so a repository without one says "queue": false in its protected.json entry or pubkit.json protect block, or `pubkit protect --no-queue`, and keeps requiring an up-to-date branch. `pubkit protect --check` and the board report a repository whose ruleset does not match
- The pull request workflow pubkit sync writes (pr.yml) also runs on merge_group, the merge queue's run of a pull request, so ci / passed and release / release report on the queue's merge and a queued pull request can merge. pubrel's release workflow only reports the check there: it tags from a push to main alone
- The cache block is one map of named entries, each taking path (was dir), refresh (run, day, week, month or never), version, inputs (were unit and shared file entries), tools (were tool: entries) and unit (one pattern with {unit}; pubkit cache run takes --unit VALUE); an entry needs refresh or inputs, an unknown key fails pubkit sync naming it, each entry gets its own cache key, and actions/cache's save prunes, so pubkit cache prune is no longer a workflow step

### Fixed
- pubkit cache run no longer fails when a rule entry, or a unit value filling one, names files outside the repository: each file is named relative to its entry
- pubkit bump, the nightly's pubkit pins, pubkit sync --check and pubkit conform cover every use of pubkit at a release in a repository's workflows, generated or hand-written: its reusable workflows (such as a hand-written ci.yml calling service-ci.yml or rust-ci.yml) as well as its actions. 0.18.0 moved and checked only the actions, so a hand-written service-ci.yml pin stayed at the old pubkit unnoticed

### Internal
- pubkit's own CI runs on merge_group too, so its required checks report in the merge queue; the release tags and the wheel is built from a push to main alone, as before

## 0.18.0 - 2026-10-29

Commit `dac919c76205`; release record `pub:sha2-256:qtnzotui2p2yghkyvogwfgvbpjf4xjxordouaa3k4j2mmzy25rta`.

### Changed
- pubkit's main ruleset requires a branch to be up to date with main before it merges (strict_required_status_checks_policy true), so the tree a pull request tested is the tree main holds after the merge, the CI run on main repeats the pull request's, and tagging a release needs no tests of its own; `pubkit protect --check` reports a repository whose ruleset does not
- `pubkit new` no longer writes an empty corpus/publets/pkg.<name>/unreleased.json: pubrel 0.6 records each unreleased change in a file of its own under unreleased/, and a new package needs pubrel 0.6.0 on this machine; new packages' CI calls pubrel 0.6.0's release workflow

### Added
- A repository that deploys a static site with deploy-static gets a ci / site job in its generated pr.yml, part of ci / passed: it builds the site (pubkit.json's new site.pr_build, else site.build) and runs deploy-static at the locked pubkit with its new check-only input, which runs pubkit site check and deploys nothing, so a site that would fail to deploy fails the pull request. site.check_dir names the directory (else the dir the deploy workflow gives deploy-static) and site.url the address; sync refuses any other site setting
- actions/deploy-ssh deploys by running one command on a server over SSH, with a key the server pins to one program (a forced command reading SSH_ORIGINAL_COMMAND), a required pinned host key, an optional bundle of workspace paths sent as a gzipped tar on the command's standard input, and an optional tailnet to join first (tailscale/github-action, as tag:ci), for what is not a directory of static files: a service the server rebuilds, a unit of a deploy script
- pubkit cache and actions/cache: keep a build's slow-changing inputs for a period and its per-unit outputs under a fingerprint of what made them, by rules in pubkit.json's cache block (pubkit cache plan, run, prune)

### Fixed
- pubkit bump and the nightly's pubkit pins move every hand-written use of one of pubkit's actions (<owner>/pubkit/actions/<name>@<commit> # vX.Y.Z or @vX.Y.Z, under Sustenaut or the old schryer), such as deploy-static, to this pubkit's commit and version, so a repository bumped to 0.17.1 no longer runs 0.17.0's site check. pubkit sync --check, and so ci / passed, and pubkit conform fail while such a pin names another pubkit or another commit; one that names no version, such as @main, is left as it is and reported

### Internal
- The nightly pushes and opens its pull requests as the Sustenaut nightly GitHub App (NIGHTLY_APP_ID, NIGHTLY_APP_KEY): one token per governed repository, for it alone, with contents, pull-requests and workflows write and actions read, from actions/create-github-app-token. A fine-grained token covers one owner only, and the governed repositories moved to the Sustenaut organization. Without the app it falls back to PUBKIT_BUMP_TOKEN with a warning
- pubkit's own CI runs pubrel 0.6.0's release workflow, and its unreleased changes are files under corpus/publets/pkg.pubkit/unreleased/; the empty unreleased.json is gone
